# Codex 手机远程控制三端落地方案

## 1. 产品结论

本项目采用三端架构：Flutter 手机 App、云端 Backend、电脑端 Desktop Agent。手机 App 是远程控制台，Backend 是身份、设备和消息路由中心，Desktop Agent 是唯一能访问本机 Codex、项目目录、Shell 和 Git 的执行器。

系统不做远程桌面，不把电脑文件系统直接暴露给手机，也不让服务器直接执行用户电脑上的命令。所有本地权限保留在 Desktop Agent，Backend 只保存必要的设备状态、会话状态、消息摘要和审计记录。

```text
Flutter App
  ↓ HTTPS / WebSocket
Cloud Backend
  ↓ WebSocket
Desktop Agent
  ↓ JSON-RPC / stdio
codex app-server
  ↓
本机项目 / Shell / Git / 文件系统
```

## 2. 三端职责

Flutter App 负责用户操作体验。它提供登录、设备列表、工作区选择、会话列表、聊天输入、实时输出、审批卡片、Diff 查看和推送通知。手机端不能直接访问电脑的文件系统，也不能直接连接 `codex app-server`。

Backend 负责可信路由和状态管理。它维护用户、设备、工作区、会话、turn、审批和审计日志，并通过 WebSocket 把 App 的控制消息转发给对应 Desktop Agent。Backend 不保存完整源码，不执行 shell，不持有电脑本地工作区的绝对控制权。

Desktop Agent 负责本机执行。它连接 Backend，完成设备绑定，维护 workspace 白名单，启动和管理 `codex app-server`，把 App 指令转成 Codex 请求，把 Codex 输出和审批请求回传给 Backend。

| 端 | 负责 | 不负责 |
|---|---|---|
| Flutter App | 指令输入、实时输出、审批、Diff 查看、设备管理 | 不直接碰本机文件系统 |
| Backend | 登录、绑定、路由、状态、推送、审计 | 不执行本机命令，不保存完整源码 |
| Desktop Agent | Codex 进程、本机目录、命令审批、Git diff | 不做复杂账号体系 |

## 3. 技术选型

手机端使用 Flutter。状态管理采用 Riverpod，路由采用 go_router，HTTP 采用 Dio，WebSocket 使用 `web_socket_channel`，推送使用 Firebase Cloud Messaging。

后端使用 Node.js + TypeScript。第一版用轻量 WebSocket 服务跑通协议，产品化阶段升级为 NestJS + PostgreSQL + Redis。PostgreSQL 保存持久业务数据，Redis 维护在线连接、事件续传、任务锁和推送队列。

电脑端 Agent 使用 Node.js + TypeScript。它需要跨 Windows 和 macOS 运行，负责 WebSocket 保活、子进程管理、工作区白名单、Codex JSON-RPC 转发、Git diff 摘要和自动更新。

## 4. 核心对象

系统固定使用 6 个核心对象。

| 对象 | 含义 |
|---|---|
| `user` | 手机 App 登录用户 |
| `device` | 一台已绑定的电脑 |
| `workspace` | 电脑端允许 Codex 访问的项目目录 |
| `session` | 一次 Codex 会话，对应一个 workspace |
| `turn` | 用户发给 Codex 的一次指令 |
| `approval` | Codex 请求执行高风险动作时产生的审批单 |

`workspace` 必须由 Desktop Agent 上报，手机端不能手工输入任意路径。`absolute_path` 只保存在电脑端，Backend 保存 `workspace_id`、展示名、路径哈希和 Git remote 摘要。

## 5. 设备绑定

Desktop Agent 首次启动后进入未绑定状态，并向 Backend 申请一次性配对码。配对码有效期为 10 分钟。用户在 Flutter App 登录后输入配对码，Backend 建立 `user_id + device_id` 绑定关系。绑定成功后，Agent 保存长期 `device_token`，后续自动上线。

```text
1. Agent 启动，申请 pairing_code
2. App 输入 pairing_code
3. Backend 校验 pairing_code
4. Backend 绑定 user_id 与 device_id
5. Agent 收到 device.bound
6. Agent 保存 device_token 并进入 online 状态
```

解绑后，Backend 吊销 `device_token`。Agent 下次连接时只能重新配对，不能继续接收任务。

## 6. 实时事件协议

App、Backend、Agent 之间统一使用事件信封。每条事件必须包含 `event_id`、`type`、`created_at` 和 `payload`。业务相关事件必须带 `user_id`、`device_id`、`session_id`、`turn_id` 中的必要字段。

```json
{
  "event_id": "evt_01HY...",
  "type": "turn.delta",
  "user_id": "usr_demo",
  "device_id": "dev_01",
  "session_id": "ses_01",
  "turn_id": "turn_01",
  "created_at": "2026-05-14T10:00:00.000Z",
  "payload": {
    "text": "正在检查项目结构..."
  }
}
```

第一版协议事件固定如下。

| 事件 | 方向 | 含义 |
|---|---|---|
| `agent.hello` | Agent → Backend | Agent 上线并声明设备信息 |
| `device.online` | Backend → App | 设备在线 |
| `workspace.list` | Agent → Backend → App | 工作区列表 |
| `session.create` | App → Backend → Agent | 创建会话 |
| `turn.start` | App → Backend → Agent | 用户发送指令 |
| `turn.delta` | Agent → Backend → App | Codex 输出片段 |
| `approval.requested` | Agent → Backend → App | 请求审批 |
| `approval.resolved` | App → Backend → Agent | 用户审批结果 |
| `turn.completed` | Agent → Backend → App | 本轮完成 |
| `turn.failed` | Agent → Backend → App | 本轮失败 |
| `git.diff.updated` | Agent → Backend → App | Diff 摘要更新 |

## 7. 审批机制

所有会修改文件、执行 shell、安装依赖、删除文件、移动文件、提交代码、推送代码、访问 workspace 外路径的行为都进入审批链路。审批由 Desktop Agent 创建，Backend 只保存摘要，Flutter App 展示操作类型、影响范围和风险等级。

审批状态固定为：

```text
pending
approved
denied
expired
cancelled
```

审批超时时间为 5 分钟。超时后 Desktop Agent 向 Codex 返回拒绝结果。本版本不提供高风险动作自动批准。

## 8. 安全规则

系统默认使用最小权限模型。Desktop Agent 以普通用户权限运行，默认只允许访问 workspace 白名单目录。Backend 对每条事件校验 `user_id + device_id + session_id` 的归属关系，任何不匹配事件直接丢弃并写入审计日志。

服务器端固定规则：

- 所有连接使用 TLS。
- App 使用用户 access token。
- Agent 使用 device token。
- Workspace 绝对路径只保存在电脑端。
- Backend 不保存完整源码和大段命令输出。
- 高风险动作必须由 App 显式审批。
- 设备离线后，未完成 turn 标记为 `interrupted`。

## 9. MVP 范围

MVP 必须跑通远程控制闭环：

1. Flutter App 登录。
2. Desktop Agent 连接 Backend。
3. App 看到在线设备。
4. Agent 上报 workspace。
5. App 创建 session。
6. App 发送自然语言指令。
7. Agent 接收指令并回传流式输出。
8. 高风险动作产生审批卡片。
9. App 允许或拒绝审批。
10. turn 完成后 App 展示完成状态。

MVP 不包含团队空间、多人协作、云端执行代码、远程桌面、完整 IDE 文件编辑器和企业 SSO。

## 10. 验收标准

第一版验收以真实链路为准：

- Flutter App 可以连接 Backend WebSocket。
- Desktop Agent 可以连接 Backend WebSocket。
- App 发送的 `turn.start` 能路由到指定 Agent。
- Agent 回传的 `turn.delta` 能实时展示在 App。
- Agent 断开后，App 设备状态变为 `offline`。
- 同一 Backend 同时连接多个设备时，消息不会串设备。
- 高风险动作能生成 `approval.requested` 并等待 App 决策。
- App 拒绝审批后，Agent 收到 `approval.resolved`。
- Backend 日志不打印完整源码内容。
- Windows 本机完成一次真实 Agent 启动和消息回显。

## 11. 产品化路线

第二阶段加入真实用户系统、PostgreSQL 持久化、Redis 在线状态、Firebase 推送、Git diff 页面、Agent 自动更新和断线事件续传。

第三阶段加入团队空间、设备共享、任务模板、审批策略配置、组织审计、企业 SSO 和私有化部署。

## 12. 工程原则

本项目采用 KISS、YAGNI、DRY、SOLID 作为实现约束。第一版只实现远程控制闭环，不提前实现团队和企业能力。协议、事件类型、审批状态保持单一来源，Flutter、Backend、Agent 共享同一套语义。每个模块只承担自己的职责：App 管交互，Backend 管路由，Agent 管本机执行。
